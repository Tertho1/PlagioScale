## 1. Project Overview

**PlagioScale** is a cloud-native, microservices-based plagiarism detection platform that runs entirely locally via Docker Compose. It detects two types of academic dishonesty:

1. **Content similarity (plagiarism):** How similar are two student submissions to each other?
2. **AI-generated content detection:** Was a submission written by a human or generated by AI (e.g., ChatGPT)?

The system is designed for educational institutions where instructors create assignments, students upload files, and the system automatically computes pairwise similarity matrices and AI detection scores.

**Key differentiators:**
- Runs entirely locally — no cloud services, no paid APIs
- Hybrid ML approach combining lexical (TF-IDF), semantic (SBERT), and statistical (Jaccard) methods
- Composite AI detection blending classifier (RoBERTa), perplexity (DistilGPT2), and stylometric features
- Full microservices architecture with autoscaling, self-healing, and monitoring

---

## 2. Problem Statement

Academic institutions face growing challenges with plagiarism and AI-generated submissions:

- **Manual detection is impractical:** Comparing every pair of submissions in a class of 100 students requires 4,950 pairwise comparisons
- **Existing tools are expensive:** Turnitin, Grammarly, and similar SaaS solutions require paid subscriptions
- **AI-generated text is hard to detect:** Traditional plagiarism tools only find copied text, not AI-paraphrased or AI-generated content
- **No local deployment option:** Most tools require sending student data to external servers, raising privacy concerns

PlagioScale addresses these problems with a self-hosted, open-source platform that combines multiple detection methods.

### 6.2 Worker Service

**File:** `worker-service/worker.py` (~515 lines)

The worker is a single-process background job processor:

1. **Dequeue:** Blocking Redis `BRPOP` with 5s timeout
2. **Route:** Parses job type (`AI_DETECTION` or `BATCH_COMPUTE`) from JSON payload
3. **Process:**
   - **AI Detection:** For each submission → extract text → run `AIContentDetector.detect()` → store `ai_score` in DB
   - **Similarity:** For each submission → extract text → add to `HybridSimilarityScorer` → compute pairwise matrix → store results
4. **Retry:** Failed jobs re-enqueued up to 3 times, then moved to dead letter queue
5. **Notify:** Sends progress updates to API via HTTP POST (fire-and-forget daemon thread)

**Worker features:**
- Pre-loads ML models at startup (SBERT, DistilGPT2) to avoid cold-start delay
- Thread-safe AI detector singleton with double-checked locking
- 120s timeout on AI detection via ThreadPoolExecutor
- Skips already-scored submissions on retry (idempotent)
- Prometheus metrics on port 8001

### 6.3 Autoscaler

**File:** `autoscaler/autoscaler.py` (~321 lines)

The autoscaler runs inside its own container with access to the Docker socket:

**Scaling algorithm:**
1. Polls Redis queue depth every 5 seconds
2. If `queue_length > 10` AND `current_workers < 5` → scale UP by 1
3. If `queue_length < 3` AND `current_workers > 1` → scale DOWN by 1
4. Cooldown: 20 seconds between scale events
5. Step size: always ±1 worker per tick (conservative)

**Scaling mechanism:**
- **Scale up:** Clones the template worker container using Docker API (copies env, networks, mounts, image)
- **Scale down:** Stops most recently created workers first (sorted by `StartedAt`), with 10s timeout, then removes container

**Configuration (environment variables):**

| Variable | Default | Purpose |
|---|---|---|
| `SCALE_UP_THRESHOLD` | 10 | Queue depth to trigger scale-up |
| `SCALE_DOWN_THRESHOLD` | 3 | Queue depth to trigger scale-down |
| `MIN_WORKERS` | 1 | Minimum worker count |
| `MAX_WORKERS` | 5 | Maximum worker count |
| `COOLDOWN_SECONDS` | 20 | Minimum time between scale events |
| `POLL_INTERVAL` | 5 | Seconds between queue checks |

## 7. Machine Learning Models & Algorithms

### 7.1 Similarity Detection (Hybrid Approach)

The system uses a **three-component hybrid** to compute pairwise similarity between submissions:

#### Component 1: TF-IDF (Term Frequency–Inverse Document Frequency) — 42.5%

**What it measures:** Lexical (word-level) similarity

**How it works:**
1. Each submission's text is tokenized into words
2. `TfidfVectorizer` from scikit-learn builds a vocabulary of up to 20,000 features
3. English stop words are removed
4. Each document is converted to a TF-IDF vector: `tf(t,d) × (log((N+1)/(df+1)) + 1)`
5. Pairwise cosine similarity is computed between all vectors

**Why TF-IDF:** Fast, interpretable, captures exact word overlap. Good at detecting copy-paste plagiarism.

**Limitations:** Misses semantic similarity (paraphrasing with different words).

#### Component 2: SBERT (Sentence-BERT) — 42.5%

**What it measures:** Semantic (meaning-level) similarity

**Model:** `all-MiniLM-L12-v2`
- 33.4 million parameters
- 384-dimensional embeddings
- 12 transformer layers
- Pre-trained on NLI (Natural Language Inference) data via knowledge distillation

**How it works:**
1. Each submission is encoded into a 384-dimensional vector using SBERT
2. Encoding is batched (`batch_size=32`) for efficiency
3. Vectors are L2-normalized
4. Cosine similarity = dot product of normalized vectors: `np.dot(norm_a, norm_b.T)`
5. Results clipped to `[0, 1]`

**Why SBERT:** Captures semantic meaning — "The cat sat on the mat" and "A feline rested on the rug" would have high similarity despite sharing no common words.

**Limitations:** Slower than TF-IDF, requires GPU for large batches, may over-semanticize (detect similarity in topically related but non-plagiarized text).

#### Component 3: Jaccard Similarity (Word Bigrams) — 15%

**What it measures:** Structural (n-gram overlap) similarity

**How it works:**
1. Text is split into word bigrams (pairs of consecutive words)
2. Jaccard index = `|intersection| / |union|` of bigram sets
3. Score ranges from 0 (no overlap) to 1 (identical)

**Why Jaccard:** Captures phrase-level similarity. Two texts using the same phrases (even with different surrounding words) will have high Jaccard.

**Limitations:** Sensitive to word order changes, doesn't capture meaning.

#### Hybrid Blend Formula

```
score = w_tfidf × TF-IDF + w_sbert × SBERT + w_jac × Jaccard

Where:
  w_tfidf = alpha × (1 - jaccard_weight) = 0.5 × 0.85 = 0.425
  w_sbert = (1 - alpha) × (1 - jaccard_weight) = 0.5 × 0.85 = 0.425
  w_jac   = jaccard_weight = 0.15
```

**Why hybrid:** Each component catches what others miss:
- TF-IDF catches exact word copy
- SBERT catches paraphrasing
- Jaccard catches phrase reuse

### 7.2 AI Content Detection (Composite Approach)

The system uses a **three-component composite** to estimate the probability that text was generated by AI:

#### Component 1: RoBERTa Classifier — 50%

**Model:** `Hello-SimpleAI/chatgpt-detector-roberta`
- ~125 million parameters
- 768-dimensional hidden states
- 12 transformer layers
- Pre-trained by Hello-SimpleAI on AI vs. human text classification

**How it works:**
1. Input text truncated to 5,000 characters
2. RoBERTa tokenizes (max_length=512, truncation=True)
3. Classification head outputs: `{"label": "Human"|"AI", "score": 0.99}`
4. If label = "Human": `roberta_score = 1.0 - model_score`
5. If label = "AI": `roberta_score = model_score`

**Why RoBERTa:** State-of-the-art text classifier, specifically fine-tuned for AI detection. Captures subtle patterns in AI-generated text.

#### Component 2: Perplexity + Burstiness (DistilGPT2) — 30%

**Model:** `distilgpt2`
- 82.1 million parameters
- 6 transformer layers (distilled from GPT-2)
- 768-dimensional hidden states

**Perplexity:**
- Measures how "surprising" the text is to a language model
- Low perplexity (≤15) → text is very predictable → likely AI
- High perplexity (≥60) → text is surprising → likely human
- Formula: `perplexity = exp(cross_entropy_loss)`

**Burstiness:**
- Measures variation in sentence lengths
- Low burstiness (≤0.1) → uniform sentence lengths → likely AI
- High burstiness (≥0.8) → varied sentence lengths → likely human
- Formula: `burstiness = σ(sentence_lengths) / μ(sentence_lengths)`

**Combined secondary score:**
```
secondary_score = 0.7 × normalize_ppl(perplexity) + 0.3 × normalize_burst(burstiness)
```

**Why DistilGPT2:** AI-generated text tends to have low perplexity (the model finds it predictable) and low burstiness (uniform sentence structure). This captures a different signal than the RoBERTa classifier.

#### Component 3: Stylometric Features — 20%

Five handcrafted features measuring writing style:

| Feature | Weight | AI Signal |
|---|---|---|
| Type-Token Ratio (TTR) | 0.20 | Low TTR (repetitive vocabulary) → AI |
| Sentence Length Variance | 0.20 | Low variance (uniform sentences) → AI |
| Transition Word Rate | 0.25 | High rate (excessive transitions) → AI |
| Hedge Word Rate | 0.15 | Low rate (lack of hedging) → AI |
| Passive Voice Rate | 0.20 | High rate (excessive passive) → AI |

**Transition words detected:** firstly, secondly, furthermore, moreover, additionally, consequently, therefore, thus, hence, however, meanwhile, subsequently, in conclusion, etc.

**Hedge words detected:** perhaps, maybe, possibly, probably, likely, seems, appears, might, could, would, suggests, indicates, etc.

**Passive voice regex:** `\b(?:is|are|was|were|be|been|being)\s+\w+ed\b`

**Why stylometrics:** AI text often has distinctive stylistic patterns — overuse of transitions, lack of hedging, uniform sentence lengths — that complement the neural approaches.

#### Final Composite Score

```
composite = 0.50 × roberta_score
          + 0.30 × (0.7 × normalize_ppl(ppl) + 0.3 × normalize_burst(burst))
          + 0.20 × stylometric_score

output = clamp(composite, 0.0, 1.0)
```

**Score interpretation:**

| Score Range | Label | Badge Color |
|---|---|---|
| 0.0 – 0.3 | Likely human-written | Green |
| 0.3 – 0.7 | Possibly AI-assisted | Yellow |
| 0.7 – 1.0 | Likely AI-generated | Red |

## 8. Features

### 8.1 Assignment Management
- Instructors create assignments with name, expected count, file types, due date
- Each assignment gets a unique 8-character access code

- Runs automatically alongside similarity computation
- Scores each submission independently (not pairwise)
- Three-tier badges with markers: ✓ (human), ~ (possibly AI), ⚠ (likely AI)

### 8.5 PDF Reports
- Downloadable similarity report between any two submissions
- Shows similarity score, submission metadata, and text comparison with highlighted common words
- Generated on-demand via reportlab (preferred) or fpdf2 (fallback)

### 8.6 Cross-Batch Comparison
- Compare submissions across two different assignments
- Useful for detecting students submitting the same work to multiple assignments

### 8.7 Student Comparison
- View all pairwise scores for a specific student's submission

### 8.8 External Lookup (Simulated)
- Extracts key phrases from a submission
- Generates synthetic web and academic paper match results

### 8.9 Admin Panel
- **Stats tab:** Total users, assignments, submissions, similarity results

- **Audit tab:** Real-time audit log via Server-Sent Events

### 8.10 Email Notifications
- SMTP-based email system with configurable host/port/credentials
- Bulk email sending with connection reuse
- Pending notification queue in database

### 8.11 Dark Mode
- CSS variable-based theme switching
- localStorage persistence

- WCAG AA-compliant contrast in both themes

## 10. Authentication & Security

### 10.1 JWT Authentication
- **Secret:** `JWT_SECRET` environment variable (required)
- **Algorithm:** HS256
- **Expiry:** 24 hours
- **Claims:** `sub` (user_id), `exp` (expiry), `ver` (token_version)
- **Storage:** httpOnly cookie (primary) + localStorage fallback for JS access

### 10.2 Password Security
- **Hashing:** bcrypt with automatic salting
- **Strength rules:** Minimum 8 characters, at least 1 digit, at least 1 special character

### 10.3 CSRF Protection
- **Pattern:** Stateless HMAC double-submit cookie
- **Token:** `HMAC(CSRF_SECRET, "csrf:{user_id}")`
- **Validation:** Header `X-CSRF-Token` must match `csrf_token` cookie AND equal HMAC value
- **Comparison:** Constant-time via `hmac.compare_digest()`

### 10.4 Role-Based Access Control
- **Hierarchy:** `user(0) < teacher(1) < admin(2)`
- **Unknown roles:** Fail every check (rank = -1)
- **Session invalidation:** `token_version` column — incremented on role change → forces re-login

### 10.5 Additional Security Measures
- **CORS:** Restricted methods and headers
- **Rate limiting:** 100/min on submit, 20/min on login, 10/min on signup
- **Ownership checks:** All mutation endpoints verify resource ownership
- **Field stripping:** `file_path` and `embedding_json` never sent to clients
- **File cleanup:** Deleted assignments remove uploaded files from disk
- **WebSocket rate limiting:** 10 connections per IP per 60s

## 11. Cloud-Native Features

### 11.1 Autoscaling

**How it works:**
1. Autoscaler polls Redis queue depth every 5 seconds
2. Queue > 10 → creates new worker via Docker API (clones template container)
3. Queue < 3 → stops extra workers
4. Cooldown: 20s between scale events
5. Limits: min 1, max 5 workers

**Demonstration:** Submit 20+ files rapidly → watch new `plagioscale-worker-N` containers appear in `docker ps` → watch them disappear as queue drains.

### 11.2 Self-Healing (6 Mechanisms)

| # | Mechanism | What It Does |
|---|---|---|
| 1 | DB auto-reconnection | Background task pings DB every 30s; on recovery, calls `init_db()` |
| 2 | Dependency-aware `/health` | Returns "degraded" (not 500) when Redis or DB is down |
| 3 | Stale job recovery | Finds jobs stuck in PROCESSING >300s, retries or dead-letters |
| 4 | Failed job retry | Re-enqueues up to 3 times with backoff |
| 5 | Dead letter consumer | Scans dead letter queue every 60s, re-queues recoverable jobs |
| 6 | Alertmanager webhook | Routes alerts to API for auto-remediation |

**Demonstration:** Stop postgres container → watch API logs show "DB down" → restart postgres → watch auto-reconnection.

## 14. Performance

### 14.1 Stress Test Results

- **Average API latency:** 28ms
- **Throughput:** Handles concurrent submissions with queue-based processing

### 14.2 Optimization Techniques

- **SBERT batch encoding:** Processes 32 texts at once (10-50x faster than one-by-one)
- **Vectorized cosine similarity:** NumPy dot product instead of loop
- **Atomic Redis pipeline:** Enqueue operations are atomic (no race conditions)
- **N+1 query fix:** Single `.in_()` query instead of N individual queries
- **DB connection pooling:** pool_size=10, max_overflow=20
- **Lazy model loading:** ML models loaded on first use, not at startup
- **Pre-computed jaccard:** n-gram sets computed once, reused

## 15. Limitations

1. **No load balancing:** Single API instance — cannot handle traffic spikes beyond one server
2. **No multi-replica API:** WebSocket scaling is single-instance only (no Redis Pub/Sub)
3. **Simulated external lookup:** Does not actually query external databases or the internet
4. **No custom training:** All ML models are pre-trained — no domain-specific fine-tuning
5. **English only:** Text extraction and ML models assume English text
6. **No real-time streaming:** Batch processing only — no streaming plagiarism detection
7. **Single-host deployment:** Docker Compose only — no Kubernetes orchestration
8. **No file versioning:** Re-submission replaces the old file (no history)
9. **OCR accuracy:** pytesseract has limited accuracy on low-quality scans
10. **Memory-intensive:** Worker needs 2GB RAM for ML models

## 17. Alternatives Considered

### Why FastAPI over Django/Flask?
- **FastAPI:** Async support, automatic OpenAPI docs, Pydantic validation, faster (uvicorn)
- **Django:** Heavier, slower for API-only use, ORM overhead
- **Flask:** No async, no auto-validation, requires more boilerplate

### Why Hybrid Similarity over Pure SBERT?
- **Pure SBERT:** Slower, may over-semanticize (detect topical similarity as plagiarism)
- **Hybrid:** TF-IDF catches exact copy, SBERT catches paraphrasing, Jaccard catches phrases
- **Research support:** Studies show hybrid approaches outperform single-method for plagiarism detection

### Why Composite AI Detection over Pure Classifier?
- **Pure RoBERTa:** May miss AI text that's been lightly edited
- **Composite:** Three independent signals (classifier + perplexity + stylometrics) are more robust
- **Research support:** Ensemble methods generally outperform single models for AI detection

### Why Docker Compose over Kubernetes?
- **Docker Compose:** Simpler setup, single-command deployment, sufficient for demonstration
- **Kubernetes:** Better for production, auto-healing, rolling updates — but much more complex
- **Decision:** Docker Compose chosen for simplicity; K8s migration noted as future work
